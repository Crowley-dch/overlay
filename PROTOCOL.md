# Спецификация протокола

Версия: 1. Максимальный размер кадра: 65 536 байт payload.

## 1. Кадр

Все сообщения передаются в виде кадров. TCP — поток байтов, поэтому границы кадров восстанавливаются по фиксированному заголовку.

### 1.1. Заголовок

Фиксированная длина — 24 байта. Все многобайтные числа — в сетевом порядке (big-endian).

| Поле | Размер | Тип | Назначение |
|---|---:|---|---|
| `version` | 1 байт | uint8 | версия протокола |
| `type` | 1 байт | uint8 | тип сообщения |
| `flags` | 2 байта | uint16 | флаги (`IS_RESPONSE`, `IS_ERROR`, `IS_FRAGMENT`) |
| `request_id` | 16 байт | bytes[16] | идентификатор RPC и ключ дедупликации |
| `payload_length` | 4 байта | uint32 | длина payload |
| `payload` | переменный | bytes | сериализованные данные |

Формат упаковки в Python: `!BBH16sI` (`struct.calcsize` = 24).

### 1.2. Порядок обработки

1. Прочитать 24 байта заголовка.
2. Если `payload_length > MAX_FRAME_PAYLOAD` — отклонить **до** выделения буфера, закрыть соединение.
3. Иначе прочитать ровно `payload_length` байт payload.
4. Передать кадр в диспетчер.

### 1.3. Устойчивость к фрагментации

Реализация `FrameBuffer`:

- накапливает байты в `bytearray`;
- возвращает список готовых кадров по мере поступления;
- корректно работает с частичным заголовком, частичным payload, несколькими кадрами за одно чтение и одним кадром за несколько чтений.

## 2. Типы сообщений

| Код | Имя | Направление | Назначение |
|---:|---|---|---|
| 0x01 | PING | → | проверка доступности контакта |
| 0x02 | PONG | ← | ответ на PING |
| 0x10 | FIND_NODE_REQUEST | → | запрос контактов, близких к цели |
| 0x11 | FIND_NODE_RESPONSE | ← | ответ с контактами |
| 0x20 | STORE_REQUEST | → | сохранить подписанную запись |
| 0x21 | STORE_RESPONSE | ← | подтверждение сохранения |
| 0x30 | FIND_VALUE_REQUEST | → | поиск записи по ключу |
| 0x31 | FIND_VALUE_RESPONSE | ← | значение найдено либо контакты |
| 0x40 | TUNNEL_BUILD | → | запрос включения в туннель |
| 0x41 | TUNNEL_BUILD_OK | ← | ретранслятор принят |
| 0x42 | TUNNEL_BUILD_FAIL | ← | отказ ретранслятора |
| 0x50 | TUNNEL_DATA | → | прикладной кадр через туннель |
| 0x51 | TUNNEL_ACK | ← | подтверждение доставки |
| 0x52 | TUNNEL_CLOSE | → | закрытие туннеля |
| 0x60 | APP_MESSAGE | ↔ | прикладное сообщение |
| 0x61 | APP_ACK | ↔ | прикладное подтверждение |
| 0xFF | ERROR | ← | ошибка обработки |

Точный формат payload для каждого типа определится на соответствующих этапах (2–5).

## 3. Флаги

| Флаг | Значение | Смысл |
|---|---:|---|
| `IS_RESPONSE` | 0x0001 | кадр — ответ на запрос |
| `IS_ERROR` | 0x0002 | payload содержит ошибку |
| `IS_FRAGMENT` | 0x0004 | кадр — фрагмент прикладного сообщения |

## 4. Корреляция RPC

Каждый запрос получает `request_id` — 16 случайных байт (`secrets.token_bytes(16)`). Ответ обязан содержать тот же `request_id`.

Правила:

- ответ с `request_id`, которого нет в `pending_requests`, отбрасывается;
- по истечении тайм-аута ожидания future завершается исключением `RequestTimeout`;
- при закрытии соединения все ожидающие future завершаются `ConnectionClosed`;
- повторный ответ на тот же `request_id` отбрасывается.

## 5. Границы применимости

Протокол не обеспечивает:

- анонимность относительно глобального наблюдателя;
- защиту от неограниченной Sybil-атаки;
- сокрытие размеров и временных характеристик пакетов.

Эти свойства не заявляются и должны быть указаны в записке как ограничения.
